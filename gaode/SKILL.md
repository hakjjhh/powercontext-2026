# 周边去哪儿：基于高德的地点推荐助手

把一句自然语言需求变成一组**可核验**的地点推荐：先解析需求，再用高德工具搜地点，
逐个规划**步行路线**，最后按硬性条件过滤、按偏好排序，并用表格给出结论。

## 适用范围

- 用户在某个起点附近找某类地点（咖啡馆、餐厅、公园、便利店等）。
- 需求里带步行时间上限、推荐数量上限、排序偏好中的任意一项。
- 起点可能是经纬度，也可能是“XX 地铁站”“XX 商场”这类地名。

## 四条硬性原则

1. **一切以工具返回为准**：地点名称、地址、坐标、步行距离与时间都必须来自高德工具的返回，
   禁止编造、估算或用直线距离替代步行路线。
2. **每个候选都从同一起点独立规划**：这是一组并列备选，不是多站行程，不要串成路线。
3. **最多推荐 3 个**：用户要求更多时也只给 3 个；不足就如实说明原因。
4. **没有依据就不说**：排队情况、安静程度、营业状态等信息若工具未返回，标注“未核实”，
   不得猜测。

## 可用的高德工具

评测环境已预置高德 MCP Server 与 API Key（**不要在 Skill 或回答里写任何密钥**）。
本题需要用到其中四个：

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `maps_geo` | 地名 → 经纬度 | `address`、`city` |
| `maps_around_search` | 以坐标为中心做周边搜 | `location`（"经度,纬度"）、`keywords`、`radius`（米） |
| `maps_text_search` | 按关键词做城市内搜索（兜底） | `keywords`、`city` |
| `maps_search_detail` | 补齐某个 POI 的详情 | `id` |
| `maps_direction_walking` | 步行路线规划 | `origin`、`destination`（均为 "经度,纬度"） |

返回结构要点：周边搜/关键词搜的候选在 `pois[]`，每项含 `id`、`name`、`address`、`location`；
步行规划的结果在 `route.paths[0]`，其中 `distance` 单位为米、`duration` 单位为秒。

## 执行流程

### 第 1 步：解析需求

从用户输入中抽出五个要素，缺失的用默认值：

| 要素 | 说明 | 缺失时 |
|---|---|---|
| 城市 | 用于限定搜索范围 | 从起点或上下文推断；仍无法确定则询问 |
| 起点 | 坐标或地名 | 必须明确；地名先用 `maps_geo` 转坐标 |
| 地点类型 | 如“咖啡馆”“公园” | 用用户原话作为关键词 |
| 步行上限 | 如“15 分钟以内” | 不设上限，但仍要算真实步行时间 |
| 推荐数量 | 用户要几个 | 默认 3，且**最多 3** |
| 排序偏好 | 如“优先近一点” | 默认按步行时间升序 |

起点解析：

- 已经是 "经度,纬度" → 直接使用。
- 是地名 → 调 `maps_geo(address=起点, city=城市)`，取返回的 `location`。
- 解析不出唯一坐标 → 请用户补充更明确的起点，不要自行假设。

### 第 2 步：搜索候选地点

优先用周边搜，按步行上限换算搜索半径：

```
radius ≈ 步行上限(分钟) × 80 米      # 步行约 1.2~1.4 m/s，留一点余量
无上限时 radius = 1000
最终取 min(max(radius, 500), 5000)
```

调用 `maps_around_search(location=起点坐标, keywords=地点类型, radius=radius)`。

结果不够时按顺序补两步，每步都要重新算步行路线：

1. 半径放大到 1.5~2 倍再搜一次（最多放大两次，不超过 5000 米）。
2. 仍不够，用 `maps_text_search(keywords=地点类型, city=城市)` 兜底，
   但只保留确实位于该城市、且能算通步行路线的候选。

需要补地址、类型等字段时，用 `maps_search_detail(id=POI 的 id)`。

### 第 3 步：逐个规划步行路线

对候选按“离起点由近到远”取前 6~8 个（不足则全取），逐个调用：

```
maps_direction_walking(origin=起点坐标, destination=候选.location)
```

从 `route.paths[0]` 读取 `distance`（米）与 `duration`（秒），转成分钟时**向上取整**。

- 单个候选路线查询失败：重试一次；仍失败则标记“路线查询失败”，不得作为符合条件的推荐。
- 不要用 `maps_distance` 的直线距离冒充步行距离。

### 第 4 步：过滤、去重、排序

1. **硬性过滤**：有步行上限时，只保留 `duration ≤ 上限` 的候选。
2. **去重**：同名同址的合并为一条。
3. **排序**：
   - 用户说“优先近一点/步行最短/离我最近” → 按步行时间升序。
   - 用户提了“评分高/环境好/安静”这类工具无法核实的偏好 → 仍按步行时间升序，
     并在回答中说明“仅按步行距离排序，其他偏好未核实”。
4. **截断**：取前 `min(用户要求数量, 3)` 个。

### 第 5 步：按固定格式输出

先给一句结论，再给表格：

| 序号 | 名称 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | … | … | 620 米 | 约 9 分钟 | 步行 620 米、约 9 分钟，是本次候选中最近的咖啡馆 |

格式要求：

- 距离：小于 1000 米用“米”（取整）；1000 米及以上用“公里”（保留 1 位小数）。
- 时间：用“约 N 分钟”，由工具返回的秒数向上取整得到。
- 推荐理由必须引用工具数据（距离/时间/类型），不写没有依据的评价。

表格后补一句短说明，按实际情况选择：

- 数量不足：“范围内符合条件的只有 X 家，已全部列出；可放宽到 N 分钟或换个关键词。”
- 有信息缺口：“营业状态、排队情况未核实。”
- 查询异常：“高德查询失败/未返回结果，暂时无法给出可靠推荐，请稍后重试或放宽条件。”

## 异常与边界

| 情况 | 处理方式 |
|---|---|
| 起点无法解析 | 请用户给出更明确的起点或经纬度，不猜测 |
| 周边搜返回空 | 扩大半径重搜；仍为空则换关键词或如实说明“附近没有找到” |
| 工具返回 `failed` | 重试一次；仍失败则如实说明服务异常，不编造地点 |
| 候选全部超时 | 一个都不推荐，说明最近一个的实际步行时间，并建议放宽上限 |
| 用户要求超过 3 个 | 只给 3 个，并说明数量上限 |
| 用户追问“环境怎么样” | 如实回答“未核实”，可建议查看地图评价 |

## 禁止事项

- 禁止编造地点、地址、坐标、距离、时间、营业状态。
- 禁止用直线距离代替步行路线数据。
- 禁止推荐超过 3 个，或把超出步行上限的地点列为“符合条件”。
- 禁止在 Skill、提交物或回答中写入 API Key 等密钥。
- 禁止把多个地点串成一条行程来回答本题。
